# Спайки S1–S8

План заложил восемь спайков на этап M0 — короткие проверки рискованных мест до основной работы ([план, §26.1](../tech-plan.md#261-спайки-этапа-m0)). Отчёты по ним должны лежать в этой папке ([§28](../tech-plan.md#28-ближайшие-шаги)).

Отдельных отчётов по спайкам нет: функции сделаны сразу в коде, на допущениях плана. **Замеров на устройствах не было**, их результатов в репозитории нет. Не измерены время холодного старта и задержка клавиатуры, не проверены реальные интенты Telegram. Эталонное устройство для бюджетов производительности (план, §5) в репозитории не зафиксировано.

Этот файл фиксирует для каждого спайка, что код предполагает или делает сейчас, что осталось измерить и в каком всё состоянии.

**Статусы:**

- **решено в коде** — реализация и тесты закрывают вопрос, замер не нужен;
- **нужна проверка на устройстве** — код есть, но поведение или скорость нужно проверить на телефоне;
- **нужны данные** — нужны реальные данные или разметка владельца продукта.

Статуса «решено в коде» пока нет ни у одного спайка: код есть везде, но главный вопрос каждого спайка — замер на устройстве или реальные данные.

## Сводка

| Спайк | Что код предполагает или делает сейчас | Что осталось проверить | Статус |
| --- | --- | --- | --- |
| **S1.** «Поделиться» из Telegram | `ShareActivity` принимает `ACTION_SEND` с типом `text/plain`. Отправителя берёт из `referrer` со схемой `android-app`. URL из текста становится источником LINK, без URL источник — APP с пакетом отправителя (`CaptureService`). Отдельной обработки Telegram нет: ссылка `t.me` — обычный URL | Что Telegram кладёт в интент из личного чата, группы и канала; виден ли пакет отправителя; бывает ли ссылка на конкретное сообщение | нужна проверка на устройстве |
| **S2.** Голос | Системный диалог `RecognizerIntent` с `EXTRA_PREFER_OFFLINE` (`Voice.kt`). `SpeechRecognizer` и разрешения `RECORD_AUDIO` нет. Без распознавателя на устройстве кнопка микрофона скрыта. Остальной голосовой ввод — проверка и загрузка офлайн-пакетов языков, голосовая заметка к паузе (EXC-3) — отложен решением владельца продукта | Работает ли распознавание ru, uk, en без сети на телефоне владельца (Android 13) и на эталонном устройстве; что происходит без сервисов Google; нужна ли загружаемая офлайн-модель | нужна проверка на устройстве |
| **S3.** Календари | Правила занятости — в `BusyTimeRules` ([ADR 0009](../adr/0009-implementation-interpretations.md), п. 16). События читаются из `CalendarContract.Instances`, изменения отслеживает `ContentObserver` (`CalendarRepository`). Тесты работают на синтетическом `FakeCalendarProvider`, а не на данных реальных календарей | Как Google Calendar, Samsung Calendar и Outlook заполняют доступность, события на весь день и статус участия. Снять фикстуры с реальных устройств | нужна проверка на устройстве |
| **S4.** Быстрый ввод | `QuickCaptureActivity` — полупрозрачная активность только со строкой ввода; клавиатура открывается сразу (`stateAlwaysVisible`). Её открывают виджет, плитка и ярлыки. E2E-тест `QuickCaptureE2eTest` проверяет, что задача из быстрого ввода виджета сохраняется за два касания и текст, но время не меряет. `StartupBenchmark` меряет только старт главного экрана | Время от тапа по виджету до готовой клавиатуры; бюджет плана — 500 мс (§13) | нужна проверка на устройстве |
| **S5.** Холодный старт | Модуль `:baselineprofile`: `BaselineProfileGenerator` и `StartupBenchmark` (холодный старт до первого кадра «Сегодня», без компиляции и с Baseline Profile, 10 повторов). Ночной workflow запускает оба на управляемом эмуляторе Pixel 6 с API 34; по его же комментарию, на эмуляторе цифры показывают только тренд. Профиля в репозитории ещё нет: каталога `app/src/main/generated` нет. Метку готовности ставит `ReportDrawnWhen` в `TaskerApp`: первый кадр со строкой ввода или с экраном на её месте (блокировка, вопрос о восстановлении, онбординг). `StartupBenchmark` пишет и `timeToInitialDisplayMs`, и `timeToFullDisplayMs`. План (§20) ставит метку после фокуса строки ввода, но на главном экране строка фокус сама не получает | Время холодного старта на эталонном телефоне с профилем и без; цель плана — не больше 1,5 с | нужна проверка на устройстве |
| **S6.** ИИ-дозаполнение | `tools/ai-eval` прогоняет маршрут enrich по набору `docs/ai-eval/enrich-v1.jsonl`: 216 формулировок, по 72 на ru, uk и en. Эталонные ответы — черновик (DRAFT), их предложил Claude. Отчётов прогона (`docs/ai-eval/report-*.md`) в репозитории нет | Владелец размечает эталоны по своим длительностям; затем платный прогон с ключом API: точность S/M/L и дат, задержка p50 и p95, стоимость вызова | нужны данные |
| **S7.** Поиск на ru и uk | FTS4 с `unicode61`. Нормализация в `SearchNormalizer`: стеммер Snowball для ru и en, собственный `UkrainianLightStemmer` для uk, термины запроса ищутся по префиксу. `SearchNormalizerTest` проверяет отдельные примеры | Качество поиска на наборе реальных запросов по тестовому корпусу; скорость — цель плана до 100 мс на 10 000 задач (§15), теста на неё нет | нужны данные |
| **S8.** Claude API с устройства | Прямой режим использует официальный Anthropic Java SDK 2.68.0 (`core:ai-claude`). Для R8 написаны консервативные правила `META-INF/proguard/anthropic-sdk.pro`: целиком сохраняются нужные пакеты SDK и Jackson. Таймаут запроса — 60 с, 2 повтора | Работает ли релизная сборка с R8 на телефоне с minSdk 26 (Android 8.0) и новее; сколько SDK добавляет к размеру APK; можно ли сузить правила R8 | нужна проверка на устройстве |

## Чем проверять

| Спайк | Что уже есть в репозитории |
| --- | --- |
| S1 | `CaptureLogicTest` (`feature:capture`) проверяет разбор присланного текста, `CommandsTest` (`core:data`) — что ссылка и приложение-отправитель сохраняются источниками задачи. `ScenariosTest` (`app`, сценарий 1) отправляет текст в `ShareActivity` с `referrer` Telegram — но это интент, собранный в тесте. Для реального Telegram нужен телефон и журналирование входящего `Intent` |
| S2 | Ничего: нужен прототип на 3–4 устройствах, как описано в плане |
| S3 | `FakeCalendarProvider` и тесты `core:calendar`: новые фикстуры с реальных устройств можно добавить туда же |
| S4 | `QuickCaptureE2eTest` проверяет путь, но не время. Нужен замер, например Macrobenchmark от тапа по виджету до показа клавиатуры |
| S5 | `./gradlew :app:generateBaselineProfile` и `./gradlew :baselineprofile:pixel6Api34GithubBenchmarkReleaseAndroidTest` с флагами из `.github/workflows/nightly.yml` — на эмуляторе. Для решения по бюджету `StartupBenchmark` нужно прогнать на эталонном телефоне |
| S6 | `./gradlew :tools:ai-eval:test` проверяет набор без вызовов API. `ANTHROPIC_API_KEY=… ./gradlew :tools:ai-eval:run` — платный прогон, около $2 за весь набор ([docs/ai-eval/README.md](../ai-eval/README.md)) |
| S7 | `SearchNormalizerTest` в `core:data`. Набора запросов и корпуса для оценки качества нет |
| S8 | `./gradlew :app:assembleGithubRelease` собирает релиз с R8. Без переменных подписи APK остаётся неподписанным ([README, «Подпись релиза»](../../README.md#подпись-релиза)). Размер APK и работу прямого режима нужно проверить на телефоне |

Когда спайк закрыт, сюда добавляют короткий отчёт: устройство, версия Android, что мерили, результат и решение. Статус в сводке меняется на «решено в коде» или на итог проверки.
